# Loader plan (Stage 4: Map and load)

Status: **begun.** The load plan, the dry run, the runner's rules and both transports (`coretransport.py`, `planningtransport.py`) are built and tested against a fake Workfront; `loader.py run --send` creates record types, fields and select options. It has not been run against a real Workfront: see "Verified by the owner" and "Still unverified" below.

## What the Loader is

Stage 4 takes the approved names, the scope and target decisions, the consolidations and the saved records, and creates the target in Workfront: first the structure (record types, fields, select options), then the records. It is built in steps, each safe to stop after.

| Step | What | Status |
| --- | --- | --- |
| 4a | **The load plan and the dry run**: everything that would be created, with temporary IDs and a status; the runner's rules (sandbox by default, idempotent, one failure never stops a run) | **Built** |
| 4b | **Field creation in the sandbox**: real Planning and Core transports (separate modules, each with its own authentication), the ID map table, every create recorded against its temporary ID | **Built and tested against a fake Workfront; not yet run for real.** Links are the second pass. Attaching Core fields to a form stays manual |
| 4c | **Record load order and the record ID map**: Airtable record ID to Core object ID and Planning record ID, so links and attachments can be reattached | Registry built (`recordmap.py`, migration 017 applied). **Planning records pass and links pass built and tested against a fake Workfront** (`loader.py records`); not run for real. The Core objects are not built |
| 4d | **Attachments** as native Core documents (link expiry, download behavior against real Airtable is untested) | **Built and tested against a fake Workfront** (`loader.py attachments`): from the files Stage 1 saved, never from a link. Not run for real |
| 4e | **The Core to Planning publish pattern**: the write-once Planning ID field, the sync status, idempotent publish, the reconciliation report | Not started; needs sandbox proof first |

## The Load a table page (`/loadtable`)

A browser page runs the same steps as `loader.py` for ONE table: check the plan, create the record type and fields, load the records, set the links, verify the counts, and reset (see the README). The shared code is `src/tableload.py`; the server (`/api/loadtable/...`) adds the gates, the confirmation (table, stage and Workspace ID) and a background job with progress and cancel. **Rehearsal order:** check, structure (dry run, send), records (file check, dry run, send), then the same for each table its links point to, then links, then verify; reset only to start a table over. Stages are defined by the user in `config.json` (`workfront.planning`: one block per stage, each with `base_url`, `bearer_token`, `workspace_id`); the page proves the chosen stage with one read of its Workspace and shows the name. Unverified: the Workspace read (`GET /v2/workspaces/{id}`, its `name` property), Verify's Workfront count (`totalElements` from the list route) and the reset's list and delete routes come from the reference, not from a call.

## What is built (4a)

Run it read-only against the database. Nothing is sent anywhere.

```
python src/loader.py plan    --db db/migration.db --base appXXXXXXXXXXXXXX
python src/loader.py dry-run --db db/migration.db --base appXXXXXXXXXXXXXX --env sandbox
```

- **The plan** (`loadplan.py`) is an ordered list of items: Planning record types, Core custom forms, fields in each system, select options in Airtable's order, and the fields the migration adds so a Core object and its Planning record can find each other (Core object type, Core object ID, Core object link in Planning; Planning record ID and Sync status in Core). A Planning field needs its record type first, so the record type is its parent; a Core custom field exists on its own and names the form it will join later.
- **Temporary IDs** depend only on the Airtable IDs (`P-T-<table>`, `P-F-<field>`, `P-O-<field>-<choice>`, `C-F-<field>`, ...), so they are identical on every run. That is what makes a restart safe.
- **Each item has a status.** `ready`: everything is decided and approved. `hold`: a design decision is open (a derived field, a relationship, an attachment, the Core object type). `blocked`: something this tool controls is missing (table or name not approved, no target data type, scope or target undecided). The reasons are listed.
- **The runner** (`loadrun.py`) takes one transport per system. It defaults to **sandbox**; production needs the exact phrase `CREATE IN PRODUCTION` and only for a real run. It is **idempotent** (a Workfront ID is written back against the temporary ID at once, and anything that already has one is skipped), a **failure never stops the run** (the item is marked failed with a message from which any credential has been removed, and what depends on it is skipped), and **dry run is the default**.
- Only a dry-run transport exists. It reports the intent (name, type, parent), not a request body.

## Verified by the owner (17 November 2026)

**Core** (sandbox): `POST /param` needs only `name` and `dataType`; the create reply returns the new ID; displayTypes TEXT and TXTA work with any dataType; a RICH field cannot be created through the API (only in the custom form viewer); attaching a PARAM to a form (CTGY) is a **manual step** and is not done by the loader.

**Planning:** only `recordTypeId` is required to create a record (v2 createRecord); record type names are checked per Workspace, and Global record types are out of scope (none are created); a field CAN be changed in place with PATCH; **bulk record create (Postman test 5, 17 November 2026):** `POST /v2/record-types/{recordTypeId}/records/bulk` with a JSON array of `{"data": {"<fieldId>": value}}` answers 201 (all created) or 207 (some failed) with `results[]`, each holding `requestIndex` and `id`; a failed result has `status` "error" and `error` {`code`, `message`} (and can still carry an `id`), so the loader matches by `requestIndex` and treats an `error` as a failure first (only the code is kept, never the message text). The exact `status` text of a successful result was not copied, so success means "no error and an id" (provisional); authentication is a Bearer token and every setting lives in `config.json`; the description property is `description`, whose real limit is 1,024, **kept at 512 on purpose** while the loader is being proven.

## Still unverified (built on an assumption; prove in the first run)

- **Reset (`loadreset.py`, `planningtransport.delete_records` and `list_record_ids`):** the routes come from Adobe's reference (`docs/WF_Planning_v2_API_simplified.yaml`), not from a call: `GET /v2/record-types/{id}/records?page=0&size=100` (`content[]`, `totalElements`), `DELETE /v2/record-types/{id}/records/bulk` with `{"ids": [...]}` (200 or 207, `results[]` with `requestIndex`), and `GET /v2/record-types/{id}` (`primaryWorkspaceId`, checked when present). A delete result with a NOT_FOUND code counts as already gone; any other error code leaves the record, and the table's local memory is kept until the record type lists empty.

- **Planning field options by type:** numberOptions (precision only when the schema gives it; currency code from `config.json`), dateOptions `{dateFormat: "locale"}` with no time format (so a date-and-time field loses its time setting until checked), userOptions. A new record type may already have a primary field; the loader does not treat it specially.
- **Select options:** sent with their field in one call (the reference requires a non-empty list); an option's ID is read from the reply's `name`, else its `displayName`; whether options can be added, renamed or reordered later is sandbox item S4.
- **Links:** each side of a two-way pair is its own reference field with `createBackReference` false. Postman test 4 (17 November 2026) showed a back reference creates a field on the other record type, named after the first record type (the name cannot be set), and that field uses one of that record type's reference slots. The loader therefore keeps each side as its own field; the 30-field cap itself cannot be tested without a 31-link table.
- **Core:** the displayTypes SLCT, MULT and CHCK (mapped, unverified), the POPT properties, the lookup used to adopt an existing field, and how a duplicate name is refused (a 409 or a message that the name exists is treated as a conflict).
- **Duplicate record type names:** how Planning refuses one is unknown (a 409, `FIELD_DISPLAY_NAME_NOT_UNIQUE` or "already exists" text is treated as a conflict).
- **Planning records (`recordload.py`, `planningtransport.create_records` and `update_record`):** the bulk create is verified (see above); still assumed: `PATCH /v2/records/{id}` with `{fields}` for the links second pass. Also assumed: the value formats (a date as ISO text, a percentage as Airtable's fraction, a select as the option key, a link as a list of Planning record IDs) and the success `status` text. A partly failed batch (207) records its successes by `requestIndex` and fails only the failed records (reason: the error code only), which stay pending for the next run; a record with no result in the reply, or a reply that cannot be matched, is failed with a "check Planning before running again" reason and not resent, since it may exist. A whole call that is refused is split and sent one record at a time. Known limit: if the program stops after Workfront answers a batch and before the answer is written, that batch is sent again and its records exist twice; the batch size (`record_batch_size` in config.json, default 50) keeps that window small.
- **Core objects (`coreobjects.py`, `coretransport.create_object`):** the routes `/proj`, `/optask` and `/task` and the parent properties (a project: `programID` or `portfolioID`; a request: `projectID`, the Request Queue project; a task: `projectID` or `parentID`) are assumed. Whether a request needs a queue topic or other required values, and whether custom field values can be sent once the fields are on a form, are not known. A name over 255 characters fails the record.
- **Attachments (`attachments.py`, `coretransport.upload_file` and `create_document`):** assumed: `POST /upload` with a multipart part named `uploadedFile` answers `{data: {handle}}`, and `POST /docu` with `name`, `handle`, `docObjCode`, `objID` and `currentVersion {version, fileName}` creates the document. How Core treats very large files, and its upload size limit, are not known. Airtable's signed links expire, so the mover never uses them: it sends the files Stage 1 saved.
- **Type mapping** (`typemap.py`): the plan's data type text is matched to Planning v2 and Core types by label; an unknown label is refused, never guessed.

## Facts supplied by the owner (14 November 2026)

- **Planning authenticates with a Bearer token** from `config.json`. The Planning field description property is `description`; its length is 512 in the v2 reference and 1,024 in the v3 field PATCH documentation. Owner decision: the plan keeps 512 as the safer limit regardless.
- **Core create calls (templates only, from the owner's reference):** `POST /param` creates a custom field. Properties: ID, customerID, dataType (for example DATE), description, displaySize, displayType (for example MULT), extRefID, formatConstraint, isRequired, label, lastUpdateDate, lastUpdatedByID, name, refObjCode. `POST /popt` creates a select option. Properties: ID, customerID, displayOrder, extRefID, isDefault, isHidden, label, parameterID, value. The bodies are bare templates: which properties are required, the dataType and displayType per Airtable type, and the call that attaches a field to a form are still to be proven in a sandbox (S6). The community-reported objects (PARAM, POPT, CTGYPA) match these paths.
- **Core create calls, schema (owner, 14 November 2026):** both calls accept either `{"data": {...}}` or the bare object. `dataType` is one of DATE, DTTM, NMBR, CURC, TEXT, RICH. `displayType` is one of MULT, SLCT, CALC, TEXT, RDIO, CHCK, TXTA, PSWD, DTXT, TYAH, RICH. `/popt` has no enums. The schema lists no required property, no response and no valid dataType and displayType pairs.
- **Unproven working guess for the type mapping** (a hypothesis to check in S6, not used by any code): single-line text TEXT with TEXT; long text TEXT with TXTA; rich text RICH with RICH; number NMBR with TEXT; currency CURC with TEXT; date DATE with TEXT; date and time DTTM with TEXT; single select TEXT with SLCT; multiple select TEXT with MULT; checkbox TEXT with CHCK. Link, attachment, formula, lookup and rollup fields have no direct Core custom field type and stay on hold as before.
- **The 30 reference-field cap** cannot be tested without a 31-link table: a documented limitation. A back reference would use a slot on the other record type (Postman test 4), but the loader sends none.

## Decisions made (14 November 2026)

1. **Core object type per table:** recorded in a new table, `table_core_objects` (project, request or task, with who, when and why). Added by [migration 011](../sql/migration_011_add_table_core_objects.sql); applied 14 November 2026. Until a table has a row, its Core form stays on hold.
2. **A data type per system:** a new column, `field_names.core_target_type`, beside the existing `target_type` (which stays the Planning type). Added by [migration 012](../sql/migration_012_add_core_target_type.sql); applied 14 November 2026. On 17 November 2026 this was extended: the Core API needs a dataType and a displayType, so the displayType is its own column, `core_display_type` ([migration 022](../sql/migration_022_add_core_display_type.sql), with a view `field_data_types` that shows `target_type` as `planning_target_type`; the column is not renamed). The Planning value must be one of Adobe's 17 types. A default mapping per Airtable type, per-field overrides, bulk updates and the history are in [migration 021](../sql/migration_021_add_data_type_mapping.sql) and the Data types page. The plan sends each system its own type, and a value off the list is cleared by a person, never used. Migration 023 adds the reference mapping's transformation text (`rule_text`) and four more Airtable types. All three migrations are drafts until the owner applies them.
3. **Derived fields** (formulas, lookups, rollups, counts, automatic numbers, created and modified times): **on hold**. They stay on hold in the plan.
4. **Relationships:** defined by the Airtable schema and stored in the database, in `field_relationships` (one row per link field, its paired field, cardinality, which side is the real relationship, and who approved it). Added by [migration 013](../sql/migration_013_add_field_relationships.sql); applied 14 November 2026. Link fields stay on hold until it exists.
5. **Select option names follow the Core label rules** (built): they keep the original text except Adobe's unsupported characters, emoji and non-ASCII characters. An option name that breaks them is put on hold with the proposed repair; nothing renames on its own. Approved option names are stored in a new table, `option_names`, and the option IDs read back from Workfront (the Core POPT, and the Planning option) in `option_workfront_ids`: owner decision 14 November 2026, added by [migration 014](../sql/migration_014_add_option_names.sql), applied 14 November 2026. Nothing reads them yet.
6. **Migration 010 (`load_id_map`) is approved and applied**, in its revised form (four Core environments, Planning Workspaces), together with 011 to 014; migration 016 later put the Workspace in its key.
7. **The Fusion-driven marker is in every description the plan sends**: a field a recorded automation sets (Stage 3) starts with `Fusion-driven: written by scenario "X".` (or the automation, flagged, until the Fusion scenario is named), in the Planning and the Core description alike. It is computed each time from the latest saved automations, never stored, and first so a length limit cannot cut it. Whether Planning accepts a description on create, and under what property name, is Postman test 3; whether it can be changed later by PATCH is test 2.
8. **Planning limits and the Core history size are checked in the plan** (`planlimits.py`, shown in the loader's plan summary): 100 record types per Workspace, 500 fields, 20 long-text, 20 formula and 30 reference fields per record type, a 512-character description, select options with a name and unique ignoring letter case, 25,000 records per record type (from the profile counts), and the design's assumption of fewer than 200 historical objects in Core (if nothing is profiled it says the assumption is unchecked). The limits are documented, not tested: the Postman tests confirm them. A finding is a warning for a person; it never changes an item's status.
9. **Runner state lives in `load_id_map`** (`loadstate.py`, built): a `pending` row is written before every create call, `created` when the ID comes back, `failed` with a scrubbed message otherwise. If a run stops mid-call, the next run tries that item again; when Workfront refuses it because the name exists AND an earlier attempt is on record, the runner adopts the one matching item (the transport's `find_existing`). A name clash with something this tool never tried to create is reported, never adopted; two matches, none, or a failed lookup also fail rather than guess. Planning rows need the Workspace ID; `dev` and `uat` are runner stages for Planning. A dry run reads the state and lists unfinished items; it writes nothing. The real transports are still not built.
7. **Credentials:** a Core sandbox exists. The Core credential and the Planning bearer token go in `config.json` (see `config.example.json`, section `workfront`: Core per environment, Planning once with its Workspace ID; `python src/loader.py config` says yes or no for each). They are never stored, logged or sent to the browser, and `loadconfig.redact()` removes them from messages. Nothing uses them yet.

**Planning has no environments** (owner, 14 November 2026): everything migrates into a Workspace treated as isolated for Dev. If the upload is fast, the Dev Workspace is wiped and a UAT Workspace created; if not, Dev is promoted to UAT. So Core has four environments (Production api=my, Preview api=Preview, Sandbox 1 api=SB01, Sandbox 2 api=SB02; named `production`, `preview`, `sandbox1`, `sandbox2`), and Planning has Workspaces. The Planning block of `config.json` is not per environment and carries the Workspace ID, and migration 010 now labels stages `sandbox`, `production`, `dev` and `uat` with a `workspace_id`. The loader never deletes a record type, a field or a Workspace. The one thing it can delete is the records of one table, through `loader.py reset` (a dry run by default, a typed phrase to send): that is the wipe before a reload, and it is a person's step.

Still open: how the runner's single environment maps to a Core stage plus a Planning Workspace stage, what confirmation a UAT or production Planning run needs, and the request shapes below.

## Long option lists as their own record type (proposed 18 November 2026; NOT built)

**Why.** A single or multiple select field with hundreds of options (a list of cities, 540 options) is not realistic as a select field, and its options often need more data of their own. The first attempt to send one failed: Planning answered HTTP 400 "option display names must be unique" because the list held names that repeat once letter case is ignored (Planning's rule for select options). The loader now refuses such a field before sending and names the repeats (`PlanningTransport.request_for`). A record type has no such rule (see "Verified" below), so a long list belongs in a record type of its own.

**The idea.** A person authorizes a select field, field by field, to be migrated as a lookup record type instead of a select field. The tool flags fields with a long option list (a threshold the person sets, for example 50) and proposes; nothing is promoted without a decision, recorded with who, when and why. Core is out of scope for now.

**A mini load order, before the table's own fields.** For each authorized field, in this order:
1. If the lookup record type is not already registered in the database, create it with a temporary marker in its name. The ID is written to the database register as soon as it is known.
2. Make its primary field carry the incoming field's name. The planned way is to rename the record type's existing primary field (`PATCH /v2/fields/{primaryFieldId}`), not to create a new field and delete the others; whether the PATCH is allowed on the primary field is **unverified** (Postman test below).
3. Rename the record type to remove the marker. Until then a stopped run can find the half-built record type again, by the register or by either name.
4. Bulk-create one record per option (the existing bulk record call, in batches), with the option's name in the primary field. Keep the Planning record ID of each one against the Airtable choice ID (`airtable_fields.choices_json`, `id`). Only IDs are stored; no option text goes into the database, a log or a report.

Only after the lookups a table uses exist does that table's structure load. The select field is then created as a Planning **reference** field (not a select type) pointing at the lookup record type: `multiple` true for a multiple select and false for a single select, with `createBackReference` false (a one-sided link). Because the lookup records already exist, the field's values go in the table's ordinary records pass; the links second pass is not needed for these fields.

**Mapping the values.** The saved records hold the option NAME as text, not the choice ID. A value is matched to a declared choice by exact name (as Airtable does), the choice to its stored lookup record ID, and that ID is sent. Two options that differ only by case stay two lookup records unless a person merges them. A value that matches no declared option (the select-values report already finds these) needs a person's decision: add it as a new lookup record, point it at a near match, or leave it out. Nothing is decided silently.

**Several fields, one list.** Fields that draw on the same list may share one lookup record type; a person chooses that when authorizing, and the shared record type is created once.

**Built so far (18 November 2026): the decisions only.** The Lookup lists page (`/lookups`, `src/lookupstore.py`, draft migration `sql/migration_024_add_lookup_lists.sql`) lets a person flag and authorize select fields, name the lists, share a list between fields and undo it, with who, when and why. It sends nothing to Workfront and the load plan does not read it yet. Migration 024 (`lookup_lists`, `field_lookup_decisions`, `lookup_list_events`) is folded into the library, the embedded DDL and `apply_migrations.py` (owner-approved 18 November 2026, for a new database; older databases are brought up by `apply_migrations.py`). Formerly: applied.

**Still to design, and why it is not built.**

The authorization itself is stored (draft migration 024, above). Whether the existing record map (`source_records`, `target_mappings`) can hold the choice-ID keys, or a new table is needed, is to be checked first. Any new table is proposed to the owner first as a `CREATE TABLE` in the style of `sql/DatabaseSchemaLibrary.sql` plus a repeatable `sql/migration_NNN_*.sql`, and is not folded into the library, the embedded DDL or `sql/apply_migrations.py` until the owner confirms it is applied.

## Risks

- A record type delete **also deletes its records** ([Adobe](https://experienceleague.adobe.com/en/docs/workfront-fusion/using/references/apps-and-their-modules/adobe-connectors/workfront-planning-modules)); `run` and `reset` never delete a record type (`reset` deletes only the records of one table). Only the Load a table page's step 7 does, on a person's typed phrase, for one table: it attempts `DELETE /v2/record-types/{id}` and forgets the table's IDs only once Workfront confirms. A refusal (for example 403 RECORD_TYPE_IN_HIERARCHY) is shown and nothing local changes until the person chooses to forget the IDs anyway. Unverified: the route has not been run against a real Workfront, and whether other record types' link fields block the delete is not confirmed.
- A Core custom field name must be unique across the instance, which the per-table check cannot see: the loader needs a check against the instance's existing names before creation.
- Production is a deliberate extra step: sandbox by default, an exact confirmation phrase for a real production run, separate IDs per environment.
- Nothing here has run against a real Workfront instance. Every statement above about the APIs comes from documentation, not from a call.
