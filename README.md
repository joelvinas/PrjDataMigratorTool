# Airtable → Workfront Planning Migration Control Plane

Current state: **Stage 1 (Data), Stage 2 (Forms) and Stage 3 (Automations) are built and working** (version 1.14; Stages 2 and 3 are manual recorders), plus the **Field names** page (the naming rules and review), inside a **multi-page site** with a left navigation panel: Setup, Stage 1: Data, placeholder pages for Stage 2 (Forms) and Stage 3 (Automations), a slot for Stage 4 (Map and load), and the API call log pinned at the bottom. Stages 2 to 4 are **not built**; see "Roadmap and structure" below.

A small local web application that captures the **schema metadata** of Airtable bases into SQLite, computes a safe table load order, and records baseline data-profile statistics (row, null and distinct-value counts). It is the first stage of a migration from Airtable to Adobe Workfront Planning.

Python standard library only. Nothing to install. Runs on `127.0.0.1` only.

## What the tool stores (and does not store)

**The SQLite database holds metadata only. It never holds Airtable record data.** Record values can be saved to separate, temporary JSON files, but only when you tick a box on a profiling run (off by default). See "Saving record data (optional)" below.

Saved in the SQLite file:

- Schema metadata: base, table and field IDs and names, field types, which tables each link field points to, the settings that define each field (select choices, formula text, rollup and lookup definitions, currency symbol and precision, date and time formats, rating scale, number precision, descriptions), 
- Table-level details (description, primary field) and every view the schema reports (name, type, visible fields).
- Attachment statistics from profiling: per table, field and file type, the number of files, their total, smallest and largest size, and a size-band count. No filenames, links or file contents.
- Aggregate statistics per field: `row_count`, `null_count`, `cardinality`, and whether the cardinality is capped.
- The computed load order (`dependency_matrix`).
- An API call log: timestamp, endpoint path, HTTP status, duration, record *count*, and error text. Never headers, the token, or response bodies.
- Runbook entries: plain-language descriptions of failures and cycles, plus one informational audit entry for each schema ingest (which base, whether it came from the API or a JSON file, and when).

Not saved in the database, the logs or any response sent to the browser:

- Record values. While profiling, each page of 100 records is read into memory, the running counters are updated, and the page is discarded. For distinct counts the tool keeps short one-way hashes of values in memory for the duration of one table, never the values themselves, and discards them when the table finishes. The one exception is the optional, off-by-default "save records" toggle described below, which writes values to JSON files on disk and nowhere else.
- The Airtable token. It is read from `config.json` and used only in the `Authorization` header of outbound requests. It is never written to the database or logs, never included in an error message, and never sent to the browser.

## Deterministic by design

Everything the app computes is **deterministic**: the same schema and the same records always produce the same load order, row counts, null counts and cardinalities. Ties in the load order are broken by table name. Cycle detection, ordering, counting and hashing are ordinary algorithms (Tarjan's strongly-connected-components, Kahn-style topological ordering, BLAKE2b hashing).

**LLMs are not used to run the app.** No model is called, no prompts are sent, and no output is generated by AI at runtime.

The only non-deterministic parts are incidental: timestamps in logs, the timing of requests, and a small random jitter added to retry wait times (it affects how long a retry waits, never any result).

## Run it

**Windows:** double-click `start.bat`. On first run it creates `config.json` and opens Notepad so you can paste your token.

**Windows or Mac, manually:**

1. Copy `config.example.json` to `config.json`, then edit it:
   ```json
   {
     "token": "PASTE_WRITE_TOKEN_HERE",
     "scopes": ["data.records:read", "schema.bases:read"],
     "bases": [ { "name": "PASTE_BASE_NAME_HERE", "baseId": "appXXXXXXXXXXXXXX" } ],
     "db_path": "db/migration.db",
     "requests_per_second": 4.5
   }
   ```
   - `token`: your Airtable personal access token. It needs `schema.bases:read` and `data.records:read`, with access to the bases you will migrate. (The older key name `airtable_pat` is still accepted.)
   - `scopes`: a note of what the token was granted. It is shown for reference and is not sent anywhere.
   - `bases`: the bases you plan to migrate. They appear in the Step 2 picker; a single entry fills in the Base ID for you. Placeholder entries (`appXXXX...`) are ignored.
   - `db_path`: the SQLite file offered in Step 1.
   - `requests_per_second`: pacing per base, between 0.5 and 5 (Airtable's limit). 4.5 leaves a small margin.
2. In a terminal in this folder: `python server.py` (on Mac you may need `python3 server.py`).
3. Open **http://127.0.0.1:8765**. It opens on **Setup** (the old address `/index.html` redirects there). For another port: `PORT=8800 python server.py` (Mac) or `set PORT=8800 && python server.py` (Windows cmd).
4. Stop with Ctrl+C.

Pages: `/` or `/setup` (Setup), `/stage1` (Stage 1: Data), `/stage2` (Forms, the recorder), `/stage3` (Automations), `/names` (Field names), `/log` (API call log). The left panel links them; Stage 4 appears as a greyed "planned" entry. The server holds the database connection, so every page shows the same connected state; the base you choose is remembered for the browser tab (the base ID only, in `sessionStorage`) so it carries from Setup to Stage 1. A stage page with no database connected shows a notice with a link to Setup and keeps its buttons off.

Without `config.json`, or with an empty token, the page shows a setup message and still works for everything that does not call Airtable (for example, pasted schema JSON).

**Public repository note:** `config.json` and database files are listed in `.gitignore`. Never commit a real token. If one is ever pushed by mistake, revoke it at airtable.com/create/tokens.

## What it does

Steps 1 and 2 are on **Setup**; steps 3 to 6 are on **Stage 1: Data**; the call log is its own page.

1. **Connect to a database.** Opens an existing SQLite file or creates one from the schema, checks that all expected tables and columns exist, and shows row counts.
2. **Confirm token and enter a base ID.** The page shows only whether a token is configured (yes/no).
3. **Ingest schema.** From the Airtable Metadata API or pasted/uploaded JSON. Re-ingesting is idempotent (upsert on `field_id`) and never wipes profiled statistics.
4. **Review load order.** A parent-first table order built from link fields, with cycles detected and logged, plus a readable dependency graph that can be downloaded on its own as an SVG or PNG. Each link-handling option has a short explanation under the dropdown. The step also produces a **load order report** you can preview in the page and download as `.mhtml` or `.html` (see [Load order report](#load-order-report)).
5. **Run profiling.** Pages through every table (100 records per request, about 5 requests per second per base) and records `row_count`, `null_count` and `cardinality` per field. An optional toggle also saves every record to JSON files during the same pass.
6. **Saved record files.** Lists, checks and deletes the JSON files (and attachment files) written by the toggles in step 5.
7. **API call log page.** Every attempt, including retries, with filters for failures, table and purpose. It is the audit trail: every call to the Airtable API is written to it (see the exception for attachment files in CLAUDE.md).

## SQL schema changes

The schema is the original `DatabaseSchemaLibrary.sql` with **new columns added to `airtable_fields`**. Nothing was renamed or removed, and every other table is unchanged. There have been four rounds: link handling and capped cardinality (migration 001), field settings (migration 002), two new tables for table-level details and views (migration 003), and one new table for attachment statistics (migration 004).

### Updated `airtable_fields` definition

```sql
CREATE TABLE airtable_fields (
    base_id TEXT NOT NULL,
    table_id TEXT NOT NULL,
    table_name TEXT NOT NULL,
    field_id TEXT NOT NULL PRIMARY KEY,
    field_name TEXT NOT NULL,
    data_type TEXT NOT NULL,
    linked_table_id TEXT,          -- populated only for multipleRecordLinks (options.linkedTableId)
    inverse_link_field_id TEXT,    -- optional: options.inverseLinkFieldId, the paired field on the linked table
    prefers_single_record_link INTEGER, -- 1/0 from options.prefersSingleRecordLink (link fields only), NULL otherwise
    row_count INTEGER DEFAULT 0,
    null_count INTEGER DEFAULT 0,
    cardinality INTEGER DEFAULT 0,
    cardinality_is_capped INTEGER DEFAULT 0, -- 1 = cardinality is a lower bound: more distinct values than the cap
    -- Field settings from the Metadata API (all NULL when not applicable or not reported)
    field_description TEXT,        -- the description typed on the field in Airtable
    is_primary_field INTEGER,      -- 1 = the table's primary field, 0 = not, NULL = not reported
    options_json TEXT,             -- the field's full options object exactly as returned (lossless backup of everything below)
    choices_json TEXT,             -- singleSelect / multipleSelects: [{"id","name","color"}] in Airtable's order
    formula_text TEXT,             -- formula fields: options.formula (and a rollup's formula when Airtable returns one)
    referenced_field_ids TEXT,     -- JSON array: options.referencedFieldIds (formula, rollup, lookup, lastModifiedTime)
    source_link_field_id TEXT,     -- rollup / lookup / count: options.recordLinkFieldId, the link field it reads through
    source_field_id TEXT,          -- rollup / lookup: options.fieldIdInLinkedTable, the field read in the linked table
    is_valid INTEGER,              -- formula / rollup / lookup / count: 1 = valid, 0 = broken (options.isValid)
    result_type TEXT,              -- computed fields: options.result.type (what the formula, rollup or lookup returns)
    result_options_json TEXT,      -- computed fields: options.result.options (precision, date format, choices of the result)
    number_precision INTEGER,      -- number / percent / currency: decimal places (options.precision)
    currency_symbol TEXT,          -- currency: options.symbol
    date_format TEXT,              -- date / dateTime: options.dateFormat.name (for example us, european, iso, local, friendly)
    time_format TEXT,              -- dateTime: options.timeFormat.name (12hour or 24hour)
    time_zone TEXT,                -- dateTime: options.timeZone
    duration_format TEXT,          -- duration: options.durationFormat (for example h:mm:ss)
    rating_max INTEGER,            -- rating: options.max
    icon TEXT,                     -- rating / checkbox: options.icon
    option_color TEXT,             -- rating / checkbox: options.color
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_airtable_fields_table ON airtable_fields(table_id);
CREATE INDEX idx_airtable_fields_linked ON airtable_fields(linked_table_id);
```

### New tables: `airtable_tables` and `airtable_views`

Table-level details and views are metadata, so they are stored in the database.

```sql
CREATE TABLE airtable_tables (
    table_id TEXT NOT NULL PRIMARY KEY,
    base_id TEXT NOT NULL,
    table_name TEXT NOT NULL,
    table_description TEXT,        -- the description typed on the table in Airtable
    primary_field_id TEXT,         -- the table's primaryFieldId
    table_json TEXT,               -- the table object as returned, minus its fields and views (lossless for anything else)
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_airtable_tables_base ON airtable_tables(base_id);

CREATE TABLE airtable_views (
    view_id TEXT NOT NULL PRIMARY KEY,
    base_id TEXT NOT NULL,
    table_id TEXT NOT NULL,
    view_name TEXT NOT NULL,
    view_type TEXT NOT NULL,       -- grid, form, calendar, gallery, kanban, timeline, block (Gantt), ...
    view_position INTEGER,         -- 0-based position in the order Airtable listed the table's views
    visible_field_ids TEXT,        -- JSON array of Airtable field IDs the view shows (requested with include=visibleFieldIds)
    view_json TEXT,                -- the view object exactly as returned (lossless backup of everything above)
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (table_id) REFERENCES airtable_tables(table_id)
);
CREATE INDEX idx_airtable_views_table ON airtable_views(table_id);
CREATE INDEX idx_airtable_views_type ON airtable_views(view_type);
```

**What views contain.** The Metadata API lists each table's views with an ID, a name and a type. The app also asks for `include=visibleFieldIds` (and repeats the request without it if Airtable ever rejects it), which adds the field IDs each view shows for the view types where Airtable reports them (a form view normally has none). `visible_field_ids` holds Airtable field IDs, so once the Airtable-to-Workfront field crosswalk exists they translate directly. `view_json` keeps the whole view object. Views no longer in the source are kept and flagged, like fields.

**What views do not contain.** Filters, sorts, grouping, colours, field order, row height and form layout are not part of the schema response, so they are not captured. Airtable has a separate per-view endpoint that may return more detail; it is not used yet (it costs one call per view and may need an Enterprise plan).

The complete schema is in `sql/DatabaseSchemaLibrary.sql`. A new database created by the app already has every column and table.

### New table: `airtable_attachment_stats`

Attachment storage (SharePoint, Workfront Core, AEM and Box each have different limits and prices) depends on how many files there are, how large they are and what types they are. Every profiling run records this from the attachment details that Airtable already returns with each record, so it needs no download and no extra API calls, and it works with "save records" on or off.

```sql
CREATE TABLE airtable_attachment_stats (
    base_id TEXT NOT NULL,  table_id TEXT NOT NULL,  field_id TEXT NOT NULL,
    file_extension TEXT NOT NULL,   -- from the filename, else the MIME type, else 'bin'
    mime_type TEXT NOT NULL,        -- as reported by Airtable, lower case, 'unknown' if none
    file_count INTEGER NOT NULL DEFAULT 0,
    total_bytes INTEGER NOT NULL DEFAULT 0,
    min_bytes INTEGER,  max_bytes INTEGER,
    unknown_size_count INTEGER NOT NULL DEFAULT 0,   -- attachments with no size reported
    size_lt_1mb INTEGER, size_1_10mb INTEGER, size_10_100mb INTEGER, size_100mb_1gb INTEGER, size_ge_1gb INTEGER,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (field_id, file_extension, mime_type)
);
```

One row per attachment field and file type. A profiling run replaces all the rows for the tables it profiles, so running it again never double counts. The size bands use 1 MB = 1,048,576 bytes. It holds no filenames, links or file contents.

Where to see it: step 5 has an **Attachments** panel (totals, size bands, by file type, by table) and **Download attachment stats .csv**, and the load order report has section 3c. The same numbers are at `/api/attachments/stats`.

What it counts: an attachment is counted once for each cell it appears in. The size is the size Airtable reports for the original file; Airtable keeps thumbnails separately and they are not counted. File-version history (if any) is not part of the API and is not counted.

### Upgrading an existing database

Easiest, with Python only (no SQLite client needed):

```
python sql/apply_migrations.py path/to/your.db
```

It adds only the columns and tables that are missing, so it is safe to run more than once, and it never changes existing data. ### What the new columns mean

| Column | Meaning |
|---|---|
| `prefers_single_record_link` | `1` = the link field holds a single record (the "many-to-one" side), `0` = many, `NULL` = not a link field or not reported. |
| `cardinality_is_capped` | `1` = more distinct values than the cap, so `cardinality` holds the cap and means "more than this". `0` = exact. |
| `field_description`, `is_primary_field` | The field's description, and whether it is the table's primary field (from the table's `primaryFieldId`). |
| `options_json` | The field's complete `options` object exactly as the Metadata API returned it. This is the lossless record: if a setting has no dedicated column (or Airtable adds one later), it is still here. |
| `choices_json` | Select choices (`id`, `name`, `color`) in Airtable's order. |
| `formula_text`, `referenced_field_ids`, `is_valid` | A formula's text, the fields it reads, and whether Airtable reports it as valid. |
| `source_link_field_id`, `source_field_id` | For rollups, lookups and counts: the link field it reads through, and the field read in the linked table. |
| `result_type`, `result_options_json` | What a computed field returns (for example `number` with `precision`, or a date format). |
| `number_precision`, `currency_symbol` | Decimal places for number, percent and currency fields; the currency symbol. |
| `date_format`, `time_format`, `time_zone` | Date and date-time formats and the time zone. |
| `duration_format`, `rating_max`, `icon`, `option_color` | Duration format; rating scale; icon and colour for rating and checkbox fields. |

**Settings are only as complete as the Metadata API makes them.** A rollup's aggregation function (such as `SUM(values)`) may not be returned by Airtable when reading; if it is, it is in `formula_text` and `options_json`. After your first real pull, check one rollup field's `options_json` to confirm what Airtable returned.

The settings appear in a **Settings** column in Step 3 and in the report's schema inventory, and **Download fields and settings .csv**, **Download tables .csv** and **Download views .csv** (Step 3) export the field, table and view details for use in field mapping. `test/sample_schema_field_options.json` is a sample schema with one of nearly every field type, for testing.

## Saving record data (optional)

The migration has to move the actual rows, so the profiling pass can also write them out. **This is off by default.** In step 5, tick **Also save every record to JSON files during this run**.

- **One pass, not two.** The profiler already reads every page of every table. With the box ticked, the same pages are also written to disk, so the number of API calls does not change. With the box unticked nothing is written, which is the way to do a test run without holding data on disk.
- **Where.** One JSON file per table: `data_extract/<base id>/<table id>.json` next to `server.py` (change it with `"extract_dir"` in `config.json`). The folder is in `.gitignore`.
- **Format.** Each file is one JSON document: `format`, `base_id`, `table_id`, `table_name`, `captured_at`, `fields` (field ID, name, type), `records` (Airtable's own record objects: `id`, `createdTime` and `fields`, keyed by **field ID**) and `record_count`. Values are exactly as Airtable returns them (linked records are record IDs, attachments are Airtable's attachment objects). Airtable omits empty cells, so an empty field is simply absent from a record.
- **Safe to interrupt.** A table is written to a `.tmp` file and renamed only after every page was read and its statistics were saved. A failed or cancelled table leaves its earlier file untouched and no `.tmp` behind. A record returned twice while paging fails that table with a clear message.
- **Manifest.** `data_extract/manifest.json` lists each file with its record count, size, SHA-256 and capture time. It holds no values. Step 6 shows it, including whether each file's record count matches the table's latest profile.
- **Where values go.** Only into these files. Never into SQLite, the API call log (which records counts only), runbook entries, error messages, the report, any CSV export or any response to the browser; the page shows counts, sizes and checksums. The tests check this by searching every one of those places for values taken from the files.
- **Deleting.** Step 6 has **Delete saved record files** (all bases, or one). Deleting the folder by hand has the same effect.
- **Select values: in the data, not in the schema.** Step 6's **Check select values** reads the saved files and compares, for every single and multiple select field, the values the records really hold with the options the schema declares (`POST /api/select-values`). It needs the records saved in step 5, so tick "Also save every record to JSON files" on the pull. It reports, per field, how many values are not declared options, how many records hold them, how many are near matches (the same apart from case or spacing, with the declared option named), the declared options no record uses, and example record IDs. The text of an undeclared value is never returned, shown, stored or logged: it stays in the saved file. Tables marked out of scope are skipped, and a table with no usable file is listed as not checked.
- **Limits.** Each file is loaded whole by whatever reads it next, which is fine for thousands of rows and needs care for millions. Attachment links inside the JSON are temporary links from Airtable and expire after a few hours (see the next section for downloading the files).

The files hold real record values. Keep them in a location that suits your organisation's data-handling rules, and delete them when the migration no longer needs them.

### Downloading attachment files (optional)

Airtable's attachment links are signed and expire after a few hours, so the files have to be fetched in the same pass that reads the records. Under "Also save every record", step 5 shows a second box, **Also download the attachment files**. It is off by default and only available when saving records is ticked, because the files are matched to records through the saved JSON.

- **Where and what name.** `data_extract/<base id>/attachments/<attachment id>.<extension>`, for example `attAbc123.jpg`. The extension is taken from the attachment's filename (`Photo.JPG` becomes `jpg`). If the filename has no usable extension (none at all, or a name such as `.jfif`), it is taken from the MIME type Airtable reports, and as a last resort it is `bin`. Attachment IDs are unique, so every file in a base has its own name.
- **Index file.** For each table, `data_extract/<base id>/<table id>.attachments.json` lists every attachment with its record ID, field ID, attachment ID, original filename, type, size, saved file, byte count, SHA-256 and status (`downloaded`, `existing` or `failed`, with a reason). This is how the original filenames and the record each file belongs to are kept, since the saved file name is just the ID. It does not contain the Airtable links.
- **Checks.** A file is accepted only if the number of bytes received equals the size Airtable reported. Files are written to a `.part` name and renamed when complete.
- **Failures don't stop the run.** An expired or missing link (HTTP 401, 403, 404 or 410) is recorded as failed and not retried. Network errors and server errors are retried up to three times. The table still finishes, the failure count shows in the progress table and in step 6, and the reason is in the index file.
- **Re-running a table.** Files already saved with the right size are kept and not downloaded again, so running the table again fetches only what failed or is new.
- **Security.** The Airtable token is never sent to the file host, only https links on `airtableusercontent.com` or `airtable.com` are fetched, and the links are never written to the database, the call log, error messages or the browser (the browser sees counts and sizes). The index file holds filenames, which can be sensitive, so the folder deserves the same care as the record files.
- **Cost.** Downloading uses no Airtable API calls beyond the paging that profiling already does, but it can take a long time and a lot of disk space. Estimate the total from the attachment sizes in one table's index before running a big base.
- **Deleting.** Step 6's delete button removes the attachment files and index files together with the JSON files.

## How it works

**Schema is never lost.** Re-ingest upserts on `field_id` (`ON CONFLICT DO UPDATE`), so profiled statistics survive. A field missing from a re-fetched schema is kept and flagged "no longer in source". There is no dedicated column for that flag, so it is derived: every ingest stamps `updated_at` on the fields it saw, and a field whose `updated_at` is older than the newest in its base is "no longer in source". For this to hold, **profiling does not touch `updated_at`**. Fields no longer in the source are left out of the load order and skipped by profiling; their old statistics are kept.

**Load order.** Built from `linked_table_id` in the database, so it can be recomputed at any time without calling Airtable. A table that links to another table is the child; the linked table is its parent. Self-links are ignored for ordering and listed. Cycles are found with Tarjan's strongly-connected-components algorithm; the tables in a cycle are treated as one step, and the result is ordered parent-first with ties broken by table name. Tables in a cycle share a depth and are ordered alphabetically (deterministic, not meaningful). Each cycle writes one runbook row, and recomputing does not repeat it. A cycle means those tables need their records loaded first and their links filled in on a second pass.

**Two-way link pairs.** Airtable normally creates a reverse (inverse) link field on the linked table. Read literally, every such pair is a two-table cycle, so there are two link-handling modes:

- **Literal** (default): every link field is a dependency, exactly as stated above.
- **Resolve two-way link pairs:** a pair is detected from `inverse_link_field_id`. If exactly one side has `prefers_single_record_link = 1`, that side's table is the child and only that field orders the load. If both sides or neither side are single-record links (many-to-many, or the hint was not reported), the direction is unknown, so both fields stay as dependencies and the two tables form a cycle: they load together and their links are set in a second pass. (This follows the rule in the reference answer key: such pairs "stay a cycle".)

**Ingest audit entries.** Each schema ingest writes one informational entry to `runbook_logs` (status `RESOLVED`, component `schema_ingest:<base id>`) in the same transaction and with the same timestamp as the field rows. This is how the report states exactly where a schema came from and when, without adding a column. These entries do not appear in the "Open runbook items" list.

**Profiling rules.**

- A value is **null** if the field is missing, `null`, an empty string, or an empty list. `0` is a real value. `false` is a real value.
- **Checkbox:** Airtable omits unchecked boxes, so a missing checkbox is treated as `false` (a real value), not null. Otherwise every unchecked box would count as null, which contradicts "false is a real value".
- **Cardinality** is the number of distinct non-null values per cell, compared using canonical JSON (sorted keys). Attachments are compared by their attachment IDs. Lists are compared as returned, so order matters.
- **Memory and the cap.** Distinct values are tracked as 64-bit hashes in a set (about 70 bytes each). The default cap is **1,000 distinct values per field**, about 70 KB per field, so memory stays small even for wide tables. It can be raised per run in the UI (for example, 50,000 is about 3.5 MB per field).
- **Capped fields.** Once a field has more distinct values than the cap, tracking stops. The database stores the cap in `cardinality` and sets `cardinality_is_capped = 1`; the UI shows "capped (more than N)". A capped number is never presented as exact. `row_count` and `null_count` are always exact.
- A table's statistics are saved only after all its pages are read. A table that fails partway keeps its previous statistics.

**API calls.** One function makes every outbound call and logs every attempt (timestamp in UTC, purpose, method, endpoint path, base and table IDs, attempt number, HTTP status, success, duration, records returned, error). It retries HTTP 429, 5xx, network errors and timeouts, with up to 5 attempts, waits that start at 1 second and double up to 30 seconds, and `Retry-After` honored up to 60 seconds. It does not retry 401, 403, 404 or 422; it fails fast with a plain-language explanation (for example, 403 usually means the token lacks access to the base or scope). Requests to the same base are paced by `requests_per_second` in `config.json` (default 5, and never above Airtable's limit of 5 per second per base). A table that still fails after its retries is logged to `runbook_logs` and the run continues with the next table.

**Security.** The server binds to `127.0.0.1` only, rejects requests with a non-localhost `Host` header or a cross-site `Origin`, and requires JSON for all writes. Strings are scrubbed of anything that looks like a token before being logged or returned. The page inserts all data with `textContent`, never `innerHTML`.

## Stage 2: Form recorder

Airtable's API returns a form view's name and (sometimes) its visible fields, but **not its layout, text, hidden fields or logic**, so a form can only be documented by hand. Stage 2 (`/stage2`) is the tool for that. It has four jobs:

1. **Record the form's structure.** Choose a form view from the schema captured in Stage 1 (its Airtable view ID becomes the form key), or start a form with no view. Then add, in the order they appear: **sections and subsections**, **fields** (picked from a type-ahead list of the form's table, with an optional label, a required flag and help text), **hidden or preset fields** (the field, the preset value and where it comes from, such as a URL parameter), **headings**, **help text** and **text blocks**. Every item can have **display logic**; sections also have **skip logic** (skip this section, skip to a later section, or skip to the end). A rule is ALL/ANY of conditions on **earlier** fields, including hidden ones, because respondents never see hidden fields but logic can depend on them. Items can be moved up, down, into the previous section or out of a section.
2. **Share an audit trail.** Every save is a new, never-edited **version** (with a note and UTC date). Reports can be previewed and downloaded as `.html` or `.mhtml` for any version: the structure in order, the logic written out in words, the fields used, every link, the version history and a sign-off block.
3. **Query the critical fields.** The field usage panel answers "which forms use this field, and how?" (placed, required, hidden/preset, controls display logic, controls skip logic) across forms and, if wanted, versions, and downloads the answer as `.csv` with the crosswalk's Workfront field IDs alongside.
4. **Rebuild for the target.** Choose **Workfront Planning (DEV or PROD)** in the report. Every Airtable field is replaced by its target field (name, ID and type) through `field_crosswalk` and `workfront_fields`, so a person can copy the form into Workfront Planning. A field with no usable mapping is marked `UNMAPPED` and the report opens with "Not ready to copy" until none is left. Text, links and logic values are carried over unchanged; if a choice is renamed in the target, change the logic value there.

**Text and links.** Text boxes take Markdown: `**bold**`, `*italic*`, bulleted and numbered lists, and `[visible text](address)`. The Bold, Italic, List and Link buttons write it for you (the Link button asks for the visible text and the address separately). Airtable stores rich text in the same form, so text copied from a form pastes in cleanly. The server parses the Markdown once, so the editor preview, the saved record, the link list and the reports always agree. Link addresses are kept **verbatim** (including parentheses, as in Wikipedia addresses) and the report prints each address beside its visible text, so a paper copy still shows where the link goes. Only `http://`, `https://`, `mailto:` and `tel:` addresses are accepted; anything else is refused on save. **Links .csv** lists every link with its form, item, visible text and address, for checking that the addresses still work after the migration. Nothing typed into a form is ever inserted as HTML.

**Where it is stored.** Each version's full record is one JSON document in `form_specs.spec_json` (the audit record, format `form-spec/1`: the Markdown and its parsed form for every text). On each save, three tables are rebuilt from it so the data can be queried: `form_items` (every section and item in document order, with its Airtable field ID), `form_logic` (one row per condition) and `form_links`. Fields are stored only by Airtable field ID, so the crosswalk can change later without touching old versions. Saving content identical to the latest version creates no new version.

**What the server checks on save** (the page shows the full list): the form key and name; that every field exists in the form's base (and table, when the form has one); that a field is placed only once; that logic uses only fields placed earlier; that "skip to" points to a later section; that logic that is switched on has conditions; that sections, headings and text blocks are not empty; and that every link address is allowed.

**Not captured.** Anything Airtable does not show on the form and you do not record: the share link's prefill values are recorded only if you enter them as hidden/preset fields, and form styling is not recorded. Field-level logic values are plain text copied from the form.

## Stage 3: Automation recorder

Airtable's API does not return automations at all, so, like forms, they are recorded by hand. Stage 3 (`/stage3`) works the same way as Stage 2 (versions, reports, field usage, Markdown text with verbatim links) and has the same four jobs: record what the API cannot show, keep an audit trail, query which fields are used, and translate for the target system.

**What is recorded.** An automation is a **trigger** followed by an ordered tree of **steps**.
- **Trigger:** one of nine types (record created, updated, matches conditions, enters a view, form submitted, button clicked, scheduled, webhook, other), with its table, view, the fields it watches, a schedule, notes and, for "matches conditions", the condition group.
- **Actions:** create record, update record, find records, send email, send message, run script, send request, wait, or other. A record action has a table. Each action can list the **fields it sets (with the value), reads or uses**, and labelled **details** (recipient, subject, body, method, URL, and so on). Details are Markdown, except code, headers and raw bodies, which are kept **exactly as typed** (a script is never reformatted or read as Markdown, and appears in the report in a code block). An update step says which record it updates: the trigger record or the record of an earlier step.
- **Conditional blocks:** an `If` branch, any number of `Else if` branches and one optional last `Else` branch. Each branch has its own steps.
- **Repeating groups:** "for each" over the records found by an earlier find step, or described in words, with their own steps.
- **Conditions** are nested groups: each group is ALL (AND) or ANY (OR) of conditions and further groups, to a depth of 8. A condition tests an Airtable field or an "other value" (for example a date or a step output, typed as text) with one of 14 operators. A field can be read from the trigger record or from the record of an **earlier** create, update or find step (or repeat). The conditions of a **find** step test the records being searched, so they use that step's table only.
- Steps can be moved up, down, into the block above or out of the block they are in; branches can be reordered, and the `Else` branch always stays last.

**Where it is stored.** Each version is one JSON document in `automation_specs.spec_json` (format `automation-spec/1`). On each save four tables are rebuilt from it: `automation_items` (the trigger, every step and every branch in document order, with paths such as `2.1.2`), `automation_logic` (every condition group and condition, with its nested position), `automation_field_refs` (every field the automation tests, watches, sets, reads or uses) and `automation_links`. Fields are stored only by Airtable field ID, so the crosswalk can change later without touching old versions. Saving content identical to the latest version creates no new version.

**What the server checks on save:** the key and name; that every table and field exists in the base; that a field set or read by a step is in that step's table; that a condition's record source is an earlier step that creates, updates or finds records; that a branch has conditions (except the last `Else`); that `Else` is last and follows an `If`; that "repeat over" is an earlier find step; that trigger conditions use only the trigger record; and that every link address is allowed.

**Reports and queries.** The report lists the trigger, then the steps in order, with branches labelled If / Else if / Else, conditions written out with their nesting, the fields each step touches, the fields-used table, every link with its address, the version history and a sign-off block. Choose **Workfront Planning (DEV or PROD)** to replace every Airtable field with its target field through `field_crosswalk` and `workfront_fields`; tables show the Workfront record type learned from their mapped fields, and the report says **"Not ready to rebuild"** and marks `UNMAPPED` fields until none is left. The **target Workfront Fusion scenario** name you record appears in the report. The usage panel answers "which automations use this field, and how?" (tested in a condition, written, read, used, watched by the trigger), with `.csv` export including the Workfront field IDs. **Links .csv** lists every link.

**Not captured.** Anything Airtable shows only inside the automation editor that you do not record: run history, and the exact internal token names between steps (type them as text if you want them documented).

## Field name validator

Migration to Workfront needs every field and table name to follow a documented standard. The validator checks names that have already been renamed (or the Airtable originals) against that standard, **proposes** repairs, and flags what a person must decide. It never changes a name on its own. Status: the rules, the import, the reports, the command line and the review page (`/names`, with saved approvals and the abandon action) are built and tested. Not built yet: setting the conflict rule's effect when records are loaded (Stage 4).

**Three targets, each validated separately:** the Workfront Planning field name, the Workfront Core custom field name, and the Workfront Core custom field label. Names are ASCII-safe (an allowlist of letters, digits, spaces and hyphens, because data exported to CSV without the right encoding corrupts anything else), may not start with a digit, and must be unique within a table. Labels keep the original text except the characters Adobe documents as unsupported in labels (`[ ] ( ) : { }` and control characters) and emoji. The full list of rules, with an example for each, is in [docs/FIELD_NAMING_RULES.md](docs/FIELD_NAMING_RULES.md); it is generated from the same rule list the validator runs, so the two cannot disagree.

**Three verdicts.**

- `PASS`: complies.
- `AUTO_FIXABLE`: the only problems are the special characters `` ' " ` ~ ! @ # $ % ^ & * ( ) [ ] { } ; : < > , . / ? `` (deleted, with nothing in their place), whitespace characters (a no-break space, tab, new line, carriage return, form feed or vertical tab, each becoming a plain space), repeated or edge spaces, or a renamed table's name inside a lookup, rollup or link field's name (replaced with the table's approved new name, found through the schema, never by guessing).
- `NEEDS_HUMAN`: everything else: accents and emoji, underscores, `1Q` to `Q1`, a leading number, a duplicate name, a name that is too long, a mention of a renamed table with no schema path.

A proposed repair is shown beside the original for both non-PASS verdicts, and nothing is applied without approval. Auto-fixable repairs may be approved as a batch, the rest one at a time. If letters outside A to Z have to be removed, the proposal says so, so the spelling can be checked.

**Order.** Every in-scope table name must be approved before any field is reviewed (an unchanged name is approved in one click). Then, in a fixed order: table-name swap, character cleanup, leading digits, and last the duplicate check on the repaired names (case-insensitive, per table, covering any number of members). The middle three can be switched off to see their effect; the baseline checks cannot.

**Data presence.** Each field in a duplicate group, and each row of the report, shows the Airtable type, the number of records with a value, the null count and the cardinality (a capped cardinality is shown as `1,000+`, never as a count). A field with no values can be considered for abandoning, which is a recorded human decision. Abandon is not offered for a field that has not been profiled since it was last seen in the schema (a re-ingest means profiling again), or for a checkbox, which is never empty.

**The Field names page** (`/names`, version 1.14). Pick the base, enter your initials (every decision records who, when and why), then work down the page:

- **A. Rules and presets.** The Planning name, the Core name and the Core label are configured separately, one column each (by default they behave the same). Each has its own step toggles (table-name swap, character cleanup, leading digits), maximum length (Planning cannot exceed Adobe's documented 250), whether a name may start with a digit, the leading-digit preset and word, and extra punctuation to allow (names) or to remove (labels); labels also choose whether to keep the `1Q` style. Each name also chooses what to do with an emoji: remove it (the default) or replace it with its word. The table number prefix preset is shared. The count under each step is how many names it changes for that column. Changing a control previews the effect without saving; decisions can only be made under saved settings, so every run can be reproduced.
- **B. Import.** Upload the renamed-names CSV (described below). Problems are listed on the page; a name you already approved is never overwritten.
- **C. Table names.** Approve every in-scope table name first. A table with no scope decision is shown as **undecided**, which is different from **out** (skipped, no decision needed); undecided tables are still checked. Set a table's scope and target here too. Approve one at a time (typing a different name if you want one), or approve all unchanged or all auto-fixable names in one click. Field review stays locked until every in-scope table is approved.
- **D. Field review.** One grid per name (Planning name, Core name, Core label) with the original, your imported name, the proposed repair, the check and reasons, the data presence and the status. Approve a name as proposed or type another; the server re-checks it, including its duplicate group, and refuses a name that would still collide. Flag a name for later, or withdraw an approval with a reason. Approve everything that passes or is auto-fixable in one click. An approved name that no longer passes (because a setting changed) is flagged.
- **E. Duplicate groups and consolidation.** Each group is one block with every member's original and repaired name side by side and its data presence. Rename a member or abandon one that has no values; the check runs again on what remains. **Compare values** tells you whether the duplicates really hold the same data (see below), so you can decide between abandoning one, consolidating them, or keeping both under different names. **Consolidate fields** (below the groups, also reachable from a group's *Consolidate these* button) turns several fields of one table into one (see below).
- **F. Descriptions.** Every field gets a description in the lineage syntax (see below). Edit one by hand and Save to keep your text, or Reset to return to the generated one; a description that is not in the syntax or has non-ASCII characters is flagged.
- **G. Reports.** The HTML report (preview it in the page, or download it as `.html` or `.mhtml`), and the CSVs, the summary and the rules document, or all of them as a zip.

**Consolidating fields.** Sometimes several Airtable fields should become **one** Workfront field (two names for the same data, or one concept spread over several fields). A consolidation group records the fields (2 to 8, all in one table), which one **survives**, why, and a **conflict rule** for the loader to use later when two members are both filled and differ: *a person resolves each record* (the default, so nothing is decided silently), *keep the survivor's value*, or *use the first non-empty value, survivor first*. The merged members leave the name review, the duplicate checks and the counts (the summary says how many are consolidated), the survivor is reviewed normally, and the survivor's description lists every origin (`Origins: Orders.Phone; Orders.Telephone; Orders.Tel No.`). A field can be in only one group, an abandoned field cannot join one, a field in a group cannot be abandoned, approved, flagged or described, and a group can be dissolved at any time (its history stays in `name_events`). The CSV report marks merged fields `CONSOLIDATED` with a `consolidated_into` column, and the HTML report has a Consolidated fields section. Compare the fields' values first if you are not sure they hold the same data. This uses **migration 009** (`field_groups`, `field_group_members`; [sql/migration_009_add_field_groups.sql](sql/migration_009_add_field_groups.sql)), which is part of the schema library, the embedded DDL and `apply_migrations.py`. An existing database gets the tables from `python sql/apply_migrations.py path/to/your.db` (back it up first); until then the panel says so and nothing can be saved. Endpoints: `POST /api/names/groups/create` and `/api/names/groups/dissolve`.

**Comparing the values of duplicate fields.** A duplicate group whose members all have data cannot be resolved by abandoning one, so **Compare values** reads the saved record file (the JSON written by profiling with *Also save every record* ticked) and, for every pair of members, counts the records where both are empty, only one is filled, both are filled and the same, both are filled and the same apart from list order, case, spacing or number-versus-text, and both are filled and different. It then says in plain language what that means: *never filled together* (each record has a value in at most one, so they can be merged without losing anything), *identical*, *no conflicts* (they agree wherever both are filled), or *N records differ*, and gives up to five record IDs per bucket to look up in Airtable. Emptiness follows the profiler (missing, null, an empty string or an empty list; a checkbox is never empty), an attachment is compared by file name and size, and the file's capture time and record count are shown, with a warning when it is out of step with the last profile. **Only counts and record IDs are ever returned.** The file is read into memory, compared and discarded; no value reaches the response, the database, a log or the page (the tests plant distinctive values and search for them everywhere). It needs the saved file for the table and compares 2 to 8 fields of one table. The endpoint is `POST /api/names/compare`.

**HTML report.** One self-contained document, in the same style as the load-order report, for the client and for auditors: about this report, a summary (verdicts and approval status per name, the fields breaking each rule, the names each step would change), the settings in force for each name, the table names with scope and approvals, one grid per name (original, your name, approved or proposed name, check, status and data presence), duplicate groups with every member side by side, where your names differ from what the rules alone give, the descriptions, abandoned fields, a summary of the decisions recorded (by kind and reviewer), the rules with examples, the method with suggested audit checks, and a blank sign-off block. It is built from the saved settings and decisions, every value is HTML-escaped, and it holds no record values. While any in-scope table name is unapproved it says field review has not started and stops after the table names. It is available in the page and at `/api/names/report.html` (add `download=1` to save it) and `/api/names/report.mhtml`; the command line writes the CSVs only, because it works from a spreadsheet you have not imported yet.

**Descriptions (lineage syntax).** `fielddesc.py` generates, for every field, `Source: Airtable. Origins: Orders.Amount; Customers.Name.`: the original Airtable table and field names the data comes from, so a client can trace any new field back to where it was. A plain field lists itself; a lookup or rollup lists the field it reads in the linked table, then the link field it reads through; a count lists the link field; a formula lists the fields it references. A name containing a period, semicolon or double quote is wrapped in double quotes (inner quotes doubled) so every description can be read back exactly. The setting *Include Airtable's own field description* appends it as `Airtable description: ...` (off by default). An emoji in an origin name is removed, or replaced with its word (`Hot Beverage`), as the *Emoji in generated descriptions* setting says. Descriptions are generated from the schema each time; only a hand-edited one is saved (`field_names.description`, with who, when and why in `name_events`). `validate_description()` flags empty text, control characters, non-ASCII characters and text that is not in the syntax; it will apply a length check once one is confirmed (Adobe documents no limit, so none is applied yet). The CSV report has `description`, `description_source` (generated or saved) and `description_problems` columns, and the command line takes `--include-airtable-description`.

**Abandon** is enforced by the server, not just the page: it needs a reason, and only a field that was profiled since it was last seen in the schema, has no values and is not a checkbox qualifies. Restoring an abandoned field is also recorded. Every approval, withdrawal, flag, import, abandon and settings change is a row in `name_events` (append-only, with who and when).

**Table scope and target (migration 008).** Which tables are in scope is a human decision kept apart from the ingested table definition, so a re-ingest can never overwrite it. `table_scope` records in or out with who, when and why (no row means **undecided**, which is different from out), and `table_targets` records whether an in-scope table lands in Workfront Planning only or in Planning plus Core. Both are set from section C of the page; **Out** needs a reason, and every change is also written to `name_events`. Out-of-scope tables and their fields are skipped, and any in-scope field that links to, or names, an out-of-scope table is listed for a human decision, because a link to a dropped table has nowhere to point. An existing database gets the tables from `python sql/apply_migrations.py path/to/your.db` (back it up first); until then every table shows as undecided and the scope buttons are off.

**Command line** (read-only: the database is opened read-only and no record value is read):

```
python fieldnames_io.py --db db/migration.db --base appXXXXXXXXXXXXXX --import renames.csv --out out/names
```

- `--import` takes a CSV with the headers `field_id, old_name, new_name, new_label, old_dataType, new_dataType`, matched to the database by Airtable field ID. `new_name` is validated as both the Planning name and the Core name; `new_label` as the label. Unmatched, repeated or blank IDs, fields missing from the spreadsheet, a stale `old_name`, and a data type that disagrees with the database are listed in `names_import_problems.csv`. A file that is not UTF-8 is read as Windows-1252 and the summary says so.
- It writes `names_report.csv` (every field: verdict, rules, proposed repair and reasons for each target, plus data presence), `names_diff.csv` (where your names differ from what the rules alone produce), `names_duplicates.csv`, `names_tables.csv`, `names_import_problems.csv`, `names_summary.txt` (counts per verdict and per rule, and how many names each step changed) and `FIELD_NAMING_RULES.md`. The CSVs open in Excel as UTF-8, and a cell that Excel would treat as a formula is prefixed with an apostrophe.
- Table approval: the command line reads approved table names from migration 007's `table_names`. Until every in-scope table is approved it writes the table report and stops with exit code 2. `--draft` previews the field results anyway and marks the summary DRAFT.
- Emoji: `--emoji-mode remove|word` for names and labels (per name with `--target-option core_label.emoji_mode=word`) and `--description-emoji-mode remove|word` for descriptions. The word is the emoji's official Unicode name in title case, so the result is deterministic.
- Per-name options: `--target-option planning_name.allow_leading_digit=true`, `core_name.max_len=200`, `planning_name.extra_allowed=&`, `core_label.extra_blocked=%` (repeatable; the names are `planning_name`, `core_name`, `core_label`). A value that is not allowed (Planning above 250, letters as extra punctuation) stops the run with the reason.
- Other options: `--table-prefix drop|end|plain` (what to do with a number prefix such as `1.2.3 Orders`; the default moves it to the end), `--digit-style move_to_end|prefix_word` with `--digit-word`, `--no-table-swap`, `--no-char-cleanup`, `--no-leading-digits`, `--label-convert-quarter`, and `--skip-table ID` (repeatable).

**Schema (migration 007).** [sql/migration_007_add_field_names.sql](sql/migration_007_add_field_names.sql) adds three tables and changes nothing that exists: `field_names` (one row per Airtable field ID: chosen names, approval state per target, description, target type, abandon decision and audit fields), `table_names` (the approved new table names) and `name_events` (an append-only record of every approval, rejection and abandon, and of the settings in force, with who, when and why). It is part of `DatabaseSchemaLibrary.sql`, the DDL embedded in `server.py` and `apply_migrations.py`, so a new database has the tables and an older one gets them from `python sql/apply_migrations.py`. No record values are stored.

**Limits not confirmed by Adobe.** The Planning field name limit of 250 characters is documented. The documentation states no length limit for Core custom field names or labels, so 255 is a placeholder, and the list of reserved names is empty until an authoritative source is found. Adobe requires a Core custom field API name to be unique across the whole Workfront instance; the validator checks uniqueness within a table only, and the cross-table check is a separate step.

**Tests.** `python test/run_regression.py names` runs the validator's suites (the pure rules; the import, database loader, reports and command line; the saved decisions; the descriptions; emoji handling; value comparison; and consolidation rules) with fabricated names only, and `namesapi` tests the page's endpoints against the mock server. `namesui` drives the real page in Chromium through the whole workflow (the table-approval gate, initials, previewing and saving settings, the emoji option, filters, approving, duplicate groups and value comparison, withdrawing, importing, descriptions, scope, the report preview and downloads, and that a hostile field name never runs) and, like the other browser suites, is skipped when Playwright is not installed.

## The loader (Stage 4, begun)

Stage 4 will create the target in Workfront. Only the first step is built: a **load plan** and a **dry run**, which send nothing anywhere. Full detail, including what Adobe's documentation confirms and what is not verified, is in [docs/LOADER_PLAN.md](docs/LOADER_PLAN.md).

```
python loader.py plan    --db db/migration.db --base appXXXXXXXXXXXXXX
python loader.py dry-run --db db/migration.db --base appXXXXXXXXXXXXXX --env sandbox
```

- **`plan`** (read-only) writes `load_plan.csv` and a summary: every Planning record type, Core custom form, field and select option (in Airtable's order) the migration would create, plus the fields that link a Core object to its Planning record, each with a **temporary ID** that depends only on the Airtable IDs (so it is the same on every run) and a **status**: `ready`; `hold` (a design decision is open: a derived field, a relationship, an attachment, the Core object type); or `blocked` (a table or name is not approved, there is no target data type, or scope or target is undecided), with the reasons.
- **`dry-run`** walks the plan the way a real run would and says what it would create. The environment defaults to **sandbox**; a production dry run is allowed because it changes nothing, but a real production run will need the exact phrase `CREATE IN PRODUCTION`.
- **The runner's rules** are built and tested with a fake transport: a Workfront ID is written back against the temporary ID at once, so a restart creates nothing twice; one failed item never stops the run (its message has any credential removed, and what depends on it is skipped); dry run is the default.
- **`run` is refused** with an explanation: creating anything is not implemented, because the request shapes for Workfront Planning and Workfront Core are not verified and no credentials are configured.
- **Select option names** follow the label rules; a name that breaks them is put on hold with the proposed repair.
- **Credentials:** the `workfront` section of `config.json` (see `config.example.json`) holds the Core credential per environment and the Planning bearer token and Workspace ID (Planning has Workspaces, not environments). `python loader.py config` says only whether each is configured. They are never stored, logged or shown in the browser. Nothing uses them yet.
- **Schema added for the loader (applied and folded into the schema library, 2026-11-14):** migration 010 `load_id_map` (Workfront IDs against temporary IDs, per stage); 011 `table_core_objects` (project, request or task per table); 012 the column `field_names.core_target_type` (the Core data type, beside the Planning one); 013 `field_relationships` (links defined by the schema, which side is the real relationship, who approved); 014 `option_names` and `option_workfront_ids` (approved option names, and option IDs read back from Core and Planning). Nothing reads them yet except the migrations check. `sql/apply_migrations.py` applies 001 to 014 to an older database.

## Troubleshooting

**`{"error": "Not found."}` on a button or link, or a red banner saying the server is older than the page.** An older copy of `server.py` is still running. The page files (`setup.html`, `stage1.html`, `stage2.html`, `stage3.html`, `log.html`, the `.js` files and `style.css`) are read from disk on every request, but `server.py` is only loaded when it starts, so replacing the files does not update a server that is already running. Close the window or terminal running the app (Ctrl+C), start it again with `start.bat` or `python server.py`, and reload the page. `start.bat` also refuses to start if something is already listening on the port.

**"Port 8765 is already in use."** Another copy is running. Close it, or use another port (`PORT=8800 python server.py`, or `start.bat 8800`).

**"No database is connected yet."** Complete step 1 first. The server forgets the connection when it restarts, so connect again after a restart.

## Roadmap and structure

**Status.** Stage 1 is complete and verified against a mock Airtable and an answer key. It has not yet been run end to end against the real Airtable bases (the mock cannot show how the real attachment file host, rollup settings or very large tables behave). The multi-page site is built (version 1.11). Stage 2, the form recorder, was added in version 1.12 and Stage 3, the automation recorder, in version 1.13 (new routes and one migration each, no change to Stage 1). Both are verified against the mock and in a browser test, but not yet against real forms or automations. Stage 4 (the field crosswalk and loading) is next, and the Stage 2 and 3 target reports become useful once it exists.

| Page | URL | Purpose | Status |
|---|---|---|---|
| Setup (home) | `/`, `/setup` | Database (step 1), token and base (step 2), and the list of stages. Shared by every stage. | Built |
| Stage 1: Data | `/stage1` | Schema, load order, profiling, record and attachment capture (steps 3 to 6, plus the open runbook items) | Built |
| Stage 2: Forms | `/stage2` | Record Airtable forms by hand (structure, display and skip logic, hidden fields, text and links), document them for the team, query which fields they use, and produce a rebuild report with Workfront Planning fields | Built (version 1.12) |

Decisions made:
- **Names.** "Data" (parallel with Forms and Automations, the kinds of thing being migrated). Only the navigation label and page headings carry the name; the URLs are `/stage1` to `/stage3` so a rename never breaks them.
- **Step numbers.** Stage 1 keeps steps 3 to 6; Setup holds steps 1 and 2.
- **Index.** Setup is the home page. `/index.html` redirects to `/`.
- **Technical shape.** Standard-library Python plus plain HTML, CSS and JavaScript, no build step and no dependencies. Separate `.html` files share one stylesheet and `common.js` (API helper, base labels, base picker, version check, navigation, connection check), each with its own script. The server serves them from a fixed list of names in `STATIC`; nothing from a request is joined into a file path.
- **Shared state.** The server holds the database connection and every page re-checks it on load. The chosen base ID is remembered per browser tab. Neither the token nor any record value is ever kept in the browser.
- **Audit.** Every call to the Airtable API goes through one function that logs each attempt to `api_call_log`; the log has its own page. New calls must do the same.

Open for later: where the open runbook items belong once Forms and Automations add their own entries (today they are at the end of step 4 on Stage 1).

Rules that carry into every stage are in `CLAUDE.md`.

## Assumptions and scope

- `field_id` is the primary key, so field IDs are assumed unique across bases (Airtable IDs are). Ingesting field IDs that are already stored under another base is refused.
- A relative database path is resolved next to `server.py`.
- Link fields that point at a table not yet in the database (for example, the other base was not ingested) are listed as "unresolved" and ignored for ordering.
- Schema fetch is one Metadata API call per base; the token must be able to see the base.
- The Workfront tables (`workfront_fields`, `field_crosswalk`) exist in the schema for the later mapping stage. Stages 2 and 3 only read them, for their target reports. Mapping fields to Workfront Planning and loading the saved records into Workfront Planning in batches of 100 are also later stages.
